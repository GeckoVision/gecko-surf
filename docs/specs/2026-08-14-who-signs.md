# Who signs, and how the check survives the signature

**Date:** 2026-08-14 · **Status:** research complete, one build proposed and unapproved ·
**Feeds:** `2026-08-14-letmebuy-agentic-loop.md` task #4

Four specialists (signing landscape, our handoff seam, Actions/Blinks, handoff security)
were asked the founder's question: *someone will need to sign at some moment — what is the
path agents actually use?* They converge, which is the most useful thing about the answer.

## The answer

```
Gecko checks  →  a signer that takes RAW BYTES  →  verify next to the key  →  submit
```

The signer is **PayBox** (MoonPay, launched 2026-07-29), reached as an MCP connector the
user adds in their chat client. Its `request_wallet_sign` carries a generic
sign-these-bytes primitive:

```
op: "solanaTransaction"
in   { "address": "<base58>", "transactionBase64": "…" }
out  { "signedTransactionBase64": "…" }
```

Base64 in, base64 out. **No rebuild, no re-stamped blockhash, no injected instruction.**
That single property is why the composition works: our attestation is taken over the
MESSAGE, and a signature does not change the message, so the check survives the signature
byte-for-byte.

Ranked, for *a real person in Claude web completing a purchase today*:

1. **PayBox** — shipping, OAuth connector, built for Claude/ChatGPT/Gemini/Grok, MPC via
   MoonX/Sodot. Grant modes: human-approval (passkey per operation) or autonomous.
2. **Pre-provisioned Privy/Turnkey/CDP/Crossmint** — proven (our own 20 mainnet
   transactions), but it is infrastructure a developer sets up outside the chat session.
3. **Solana Pay / Actions / Blinks** — mature specs, but neither Claude web nor Grok
   renders Blinks natively, so the human must leave the chat. See §"ruled out".
4. **`@orquestradev/signer-mcp`** — Berkay's own, wrapping the Solana Foundation's
   `@solana/keychain` (14 backends, audited). 0 stars, 10 commits, ~3 months stale. Note
   that when WE needed Privy signing we went straight to Privy's REST API rather than
   adopt it.

## The three findings worth keeping

### 1. No custody provider can express our predicate

Turnkey has the best policy engine available — per-method rules, amount thresholds,
program allowlists, evaluated inside the enclave. And **none of them, Turnkey included,
can say "only sign if this message hash matches a simulation someone else performed."**
The closest real analog is a static program-id allowlist, enforced *below* the receipt
rather than *bound to* it.

This is the whole-category answer to the 1claw question, not a one-vendor answer:
**custody protects the KEY, never the ACTION.** Every provider will sign a well-formed
transaction that does the wrong thing. That gap is what the receipt fills, and it is why
the verdict must sit upstream of all of them.

### 2. x402 is the right economics and the wrong protocol

The founder's store ruling — open surface, the caller signs and pays, the check is the
gate — holds exactly. But x402 **on Solana signs a fixed-amount SPL transfer that gates
the next HTTP call**. It cannot express "sign this landing bundle we already built and
simulated." Our object is a program instruction, not a paywall. Use x402 as the metaphor
for who pays; do not expect the protocol to carry the purchase.

### 3. The binding is real, and weaker than it looks

**Correction to this repo's own docs:** message-hash binding **IS built** —
`txbind.message_binding()`, `Receipt.message_binding` / `binding_strength`,
`verify_handoff(require="exact")`, and `TransactionSigner` re-verifies and re-binds.
`CLAUDE.md` and `docs/architecture.md:102,166` still say "planned"/"not built yet". Those
lines are stale and should be fixed before someone builds a second binding beside the
working one.

What the binding actually is: an **unkeyed** sha256 over
`strength ‖ 0x00 ‖ version ‖ 0x00 ‖ message_bytes`, returned **in the same tool result as
the bytes it covers**. Against corruption that is a checksum and it works. Against an
adversary who can rewrite that response, it is not a control — they recompute the digest
over their own bytes in one line.

The one comparison in this codebase whose two sides have **different origins** is
`--expect-binding` in `scripts/sign_and_send.py`, and its second origin is a human
copy-pasting between terminals. Everywhere else, "does the receipt match the bytes" is
`x == x` — a true statement with no adversarial value.

**So state the guarantee precisely:** the check is strong against a WRONG plan and
currently weak against a SUBSTITUTED one. Given we sell *check the call before it counts*,
that distinction is ours to be exact about rather than to blur.

## Ruled out: Actions and Blinks, by specification

Both the Actions spec and the Solana Pay transaction-request spec carry the same clause —
if the returned transaction has no signature, the client **MUST** ignore and overwrite the
`feePayer` and the `recentBlockhash`, and **MUST** re-serialize. That is exactly the
mutation an `exact` binding is taken against; `structural` dies too, because a fee-payer
overwrite moves the account keys rather than only the 32 blockhash bytes.

Worse than broken: **undefined.** The spec mandates the mutation, `@dialectlabs/blinks`
passes bytes through untouched, and `@solana/actions` is legacy-only and cannot parse a v0
transaction at all. Three implementations, three behaviours, no conformance suite. A
predictable break could at least be labelled; this one cannot.

The only in-band mechanism that freezes the bytes is a **pre-existing signature** — both
specs flip to "must NOT alter" the moment `signatures` is non-empty. That requires Gecko to
hold an ed25519 key, which is the constraint we are not crossing for a rendering surface.

Maturity, since it settles the question independently: `@solana/actions` last published
**2024-11-05** (~3.6k downloads/month), `@dialectlabs/blinks` last release **2025-04-04**
(~2.3k/month), Phantom ships Blinks as an experimental feature, off by default, X-only.
`@solana/pay` does ~45k/month and is being actively rewritten onto `@solana/kit`. Blinks
was a mid-2024 push in maintenance since Q2 2025.

**One adjacent hazard, worth knowing:** Phantom injects ComputeBudget instructions into
unsigned transactions it is asked to sign — unless the transaction already carries
compute-budget instructions. Our landing bundle does, so it is skipped. That is a lucky
accident of our bundle's shape, not a guarantee, and it is undocumented behaviour in other
wallets.

## The timing constraint everything must fit inside

The check expires with its blockhash, and the real budget is **~40–48 seconds**, not the
"~1 minute" the tool's own note claims: `landing.latest_blockhash` asks at
`commitment: "finalized"`, roughly 31 slots behind, so a fifth of the 150-slot budget is
spent before the caller sees the bytes.

| PayBox grant mode | Behaviour | Fits the window |
|---|---|---|
| **autonomous** | signs immediately, inside the grant | **yes, comfortably** |
| **human approval** | `pending_approval` + approval URL → passkey → poll `get_request` | **no** — the blockhash dies during approval |

So the human-approval path cannot be *prepare → approve*. It has to be
**approve → prepare → sign**, or nothing lands. Worth deciding whether
`latest_blockhash` should stay at `finalized`; `confirmed` buys back ~12 seconds against a
theoretical fork risk. Either answer is defensible — the current one is not recorded as a
choice.

## The one build proposed (UNAPPROVED)

`verify_signed_transaction(transaction, binding, network)` on the public surface —
`verify_handoff` at `require="exact"`, which already exists and is not exposed. Keyless,
stateless, roughly twenty lines of transport.

It lets anyone prove that **what PayBox signed is what Gecko checked, before broadcast.**
It cannot prevent a bad signature; it makes one detectable and un-broadcastable, which is
the strongest honest thing a party holding no key can do.

It does NOT close the substitution gap in §3 — an attacker who rewrites the response
rewrites both halves. Closing that needs a second origin, and the options, in order of
what they cost:

1. **Generalize `--expect-binding`**: carry a short human-verifiable binding prefix, have
   the agent display it, and make the signer demand it as a required argument. Installs a
   human as the second origin. Free, and it is the only control that has ever caught a
   substitution here.
2. **A pull endpoint**: `GET /attestation/<binding>` returns the receipt facts. A
   substituted transaction has a binding we never issued → 404 → refuse. No key at all;
   costs an online dependency at signing time that must fail closed.
3. **A Gecko attestation key** (ed25519 over the receipt facts, never a fee payer, never in
   a value-moving instruction). Strongest, and it is a key we hold — rotation, revocation,
   compromise story. **A founder/staff decision, not an in-lane one.**

## Non-goals confirmed

- We do not become the signer on a public surface. Unchanged.
- We do not build an Actions/Blinks endpoint for the attested path.
- We do not adopt x402 as the purchase transport.
