# Roadmap — after the e2e agentic payment

*Written 2026-08-13, after twenty mainnet transactions and the first purchase driven
end-to-end by an agent with no key on this machine.*

Three questions, in the order they block each other:

1. **Can the payment loop run over SSE, driven by Grok and Claude web?** — closes the
   current task.
2. **Where does a provider's surface run — our host, or theirs?** — the next task.
3. **Does the enclave move to 1Claw?** — falls out of (1), not out of preference.

---

## Where we actually are

**Done and proven on chain.** Comprehend → derive → simulate → receipt → policy → sign in
an enclave → submit → verify. Twenty mainnet transactions; the prediction has matched the
chain every time it was captured. `--store` now selects a store's accounts, not just its
name, so any storefront on the program is reachable.

**The hosted surface at `mcp.geckovision.tech` cannot spend, by construction.**
`gecko/prepare_purchase.py` says it in its own first line: it *"holds no key, touches no
key, and has no path to one"*, and the public docs make that claim. It returns unsigned
bytes plus a receipt bound to them.

**So the loop is currently split across two planes.** The hosted plane plans and verifies.
The founder's machine signs, using Privy credentials in its OS keychain. Grok and Claude
web can reach the first plane and not the second.

That is not a gap in the wiring. It is the design, and goal (1) proposes to change it.

---

## Goal 1 — the payment loop over SSE

### The decision that comes first

An agent in a browser chat cannot hold a key. So "the agent pays" over SSE means one of:

**(A) The hosted plane stays keyless.** Chat plans and verifies; settlement happens
wherever the key already lives. Honest today, costs nothing, and is what the docs claim —
but it is not an end-to-end agentic payment from Grok, and calling it one would be false.

**(B) The hosted plane gains a signer** — Privy or 1Claw — that signs under policy for a
wallet bound to the authenticated caller. This is what the goal actually asks for.

**(B) is a one-way door.** The moment the hosted surface can move money, every existing
control is re-scoped: a bug in the surface becomes a spending bug, the ADVISORY ledger
becomes the only velocity bound on a multi-tenant service, and "Gecko holds no key" stops
being true of the product even if it stays true of the engine.

> **RULED 2026-08-13 — (B), with (A) preserved as a mode.** Anyone may bring their own
> signer; we must also be *able* to sign, or there is no end-to-end transaction for a user
> who has no key. The keyless path does not go away — it becomes the configuration you get
> when you bring custody.

### Two enclaves, not one

The word "enclave" is doing double duty, and the two jobs have different blast radii:

| | Transaction signing | Outbound-credential custody |
|---|---|---|
| Protects | a Solana key producing a signature | the API keys Gecko injects at call time |
| Today | Privy, proven across 6 mainnet signatures | `Session.auth_headers()` → the LOCAL OS keychain |
| Hosted answer | this roadmap's item (B) | **none — `gecko auth set` has no multi-tenant story** |
| A compromise loses | transactions, bounded by policy | every customer's third-party API keys |

1Claw is aimed at the **second** column. Keep them separable even if one vendor supplies
both: losing a signer is a bounded incident; losing a credential vault is everyone's.

### Bring-your-own-signer: target `@solana/keychain`

`@orquestradev/signer-mcp` (Berkay, MIT) wraps the Solana Foundation's `@solana/keychain`
behind one MCP server with **twelve** custody backends — memory, Privy, Turnkey, AWS/GCP
KMS, Fireblocks, DFNS, Vault, CDP, Crossmint, Openfort, Para. That is our `SigningBackend`
seam, already implemented twelve times. **Target that abstraction rather than writing
integrations.** It is stdio, so it answers "the user brings custody" and not (B).

**But do not ship a configuration where the agent holds our tools and a bare signing tool
as peers.** `sign_transaction` there signs any base64 transaction with no policy, no
receipt and no binding, and `sign_and_send_transaction` broadcasts in one call — the
method we deliberately refuse, and the reason tx #12's first attempt was rejected
`policy_violation`. Two peer tools mean the agent can hold a receipt from us and sign
something else entirely; the verdict-before-signature gate stops being a gate.

**The compose ask (outward — founder sends, not us):** an optional `receipt` argument on
`sign_transaction` that refuses unless the bytes hash to the receipt's binding. Their
signer keeps twelve backends and gains a way to say no; we keep the gate without owning
custody. Same shape as the Arazzo arity proposal.

### What `prepare_purchase` needs in order for us to sign — and the inversion

Only the buyer's **public key**. Not an email, not a credential. The chain is
**account → wallet_id → pubkey**, and each hop lives somewhere different: `account →
wallet_id` is OUR record (and does not exist yet), `wallet_id → pubkey` is the custodian's
answer — *asked for, never asserted* (`scripts/privy_backend.py:253`) — and only the
pubkey enters the transaction.

**The inversion (B) forces:** today `prepare_purchase` ACCEPTS a signer pubkey from the
caller, which is correct for a keyless surface. Under a hosted signer it must be **looked
up from the authenticated session and never accepted from the caller**, or a caller names
an address they do not own. N1's three-way check (`sol_delta_account == fee_payer ==
backend.pubkey`) already refuses the mismatch at the signer — but that is the second line;
not accepting the input is the first, and both should hold.

### The fork nobody has walked into yet: WHERE the signature happens

Worth stating before someone (me) takes the obvious next step. As of #422 and the `store`
mount, mode B means **the buyer is looked up** — the caller no longer names the wallet. It
does **not** mean we sign: `prepare_purchase` still hands back UNSIGNED bytes, so the
hosted loop still stops one step short of a settled payment.

Closing that step means a tool that produces a signature. It must **not** live in
`gecko/prepare_purchase.py`. That module's first paragraph says it "holds no key, touches
no key, and has no path to one", the public docs repeat it, and it is true today — the
moment a signing path is added there for convenience, all three become false at once, on
the module that runs behind a public unauthenticated mount.

So the shape is two tools, and the separation is the safety property:

| | reachable from | holds a key |
|---|---|---|
| `prepare_purchase` | public mount AND gated mount | never |
| a settle/sign tool | the gated mount ONLY | reaches a custodian, never a key |

A settle tool is also the first thing on the hosted plane that can spend, which is what
finally makes the **durable spend ledger** (item 3 below) load-bearing rather than
theoretical: today there is no hosted call site, so there is no budget to make durable.

### What must be fixed before (B) can be safe

Ordered by whether it blocks a real user.

| # | Gap | Evidence | Blocks |
|---|---|---|---|

| 2 | **No wallet↔caller binding exists.** ~~There is no such record~~ **PARTLY CLOSED.** The record (#420) and the wire from the gate to the tool call (#422) both exist. | 3 | **The spend ledger is not durable and is advisory.** No hosted call site today; on Fargate a task replacement resets the daily cap | `FileSpendLedger`; `infra/ecs-stack.yml` declares no volumes | (B) — it becomes the only velocity bound |
| 4 | **B2's T2 residual only closes at the key holder.** An attacker with code execution can hand `simulate()` a fake node and get a genuinely stamped receipt. `Receipt.origin` closes the in-process half; the other half closes only where the signer enforces the predicate | `b2-construction-token-trap` design note | whether (B) is safer than a bare wallet |
| 5 | **No SSE resumption is possible.** The SDK keys sessions in an in-process dict, emits no `id:`, reads no `Last-Event-ID`; the 1800s cap is a scheduled disconnect | `mcp/server/sse.py:240-244` | long chats on either client |
| 6 | **No ALB stickiness.** SSE session state is in RAM; a rolling deploy can route the POST to the task that does not hold the session | `infra/ecs-stack.yml` | reliability, not safety |

**Item 4 is the one that decides 1Claw.** The question is not which vendor is nicer — it
is *can the signer's policy engine express our predicate?* Privy policies are
deny-by-default per method and we already know they can pin programs; what is unproven is
whether either vendor can express **"only sign a message whose simulation I have seen"**
and **"at most N lamports per day"** over a raw Solana message. If neither can, then
moving the counter to the key holder is not a plan, and (B) ships with the residual
documented rather than closed.

### How to test it, honestly

- **Grok:** a real client. Connect it to the hosted surface and drive the full sequence.
- **Claude web:** also a real client — connect it the same way. If it cannot be driven
  interactively for a test, the honest substitute is a **transport-level client** that
  speaks the same SSE handshake (`GET /sse` → `POST /messages/?session_id=`) and issues
  the same JSON-RPC. That proves the *transport and the tools*; it does **not** prove the
  client's behaviour — model-side tool selection, its reconnect policy at the 1800s cap,
  and its handling of a refusal are exactly what a simulation cannot tell us. Report those
  separately or not at all.
- **The 1800s cap is a per-client verification**, not a server change: does the client
  re-initialise cleanly, or surface a fatal tool error?

**Definition of done for goal 1:** a named client, over SSE, completes list → confirm →
settle against mainnet, with the signature produced by a key that never existed on the
machine running the client — or, if we choose (A), a written statement that the hosted
loop stops at the receipt and why.

## Goal 2 — the provider surface: hosted or embedded

The founder's instinct is that providers will choose embed. I think that is right for
*large* providers and wrong as a default, and the two answers are not exclusive.

**What the architecture pass already ruled** (2026-08-13): the provider **hosts their
config** at a URL and we fetch it, keeping a pointer and a content hash and never the
config bytes. That decision is about *where the truth lives* and it holds either way.
What is open is *where the engine runs*.

| Model | The provider gets | We get | Real cost |
|---|---|---|---|
| **Call us** (they point at our MCP) | zero ops, instant updates, our security layers | telemetry, one code path, the ability to fix a bug for everyone at once | we are in their critical path; their outage is our outage and vice versa |
| **Embed** (they run the engine) | no third party in the request path, their own SLA, their own data boundary | no telemetry, N versions in the wild, every bug fix is a release | support surface multiplies |

**Recommendation: offer both, but make "call us" the default and embed the earned
upgrade.** The reasons are specific rather than ideological:

- The *comprehension* step is where our value is, and it is a **build-time** activity, not
  a request-time one. A provider's surface is comprehended once and changes when their API
  changes. So the thing that must be hosted-or-embedded is mostly the *serving* of an
  artifact, which is cheap either way.
- What is genuinely request-time — the security layers, the SSRF guard, the refusals — is
  also what a provider is least likely to want to own and most likely to get wrong.
- **Embed becomes mandatory the moment a provider's request path cannot leave their
  network** (regulated data, on-prem). That is a real constraint, not a preference, and it
  is the honest trigger for the upgrade.

**The blocker nobody named, and it is ours, not theirs:** the provenance loader is
**fail-open**. A config that supplies `pdas` and omits `pda_origins` earns `extracted` —
the top of the ladder — because `_apply_origin_cap` is demotion-only
(`gecko/find_start.py:928-930`). Harmless while every config is ours and a CI test pins
the key sets; **a provider's config never runs that test.** Absence becomes a permission.
Fix that before the first external config loads, in either model.

Also unresolved and cheap to state: an admitted config **still needs a redeploy to
activate** — `serve_mcp._SURFACES` is a module-level list read at boot. Accept
redeploy-to-activate for v1 and say so plainly rather than implying live updates.

## Goal 3 — the enclave and 1Claw

Not a separate goal. It is the answer to item 4 above, and it should be decided by one
measurement rather than a vendor comparison:

> Can the policy engine express, over a **raw Solana message**, (a) a per-day lamport
> counter and (b) a constraint tied to a simulation we performed?

- If **yes** → move the velocity counter and the receipt predicate to the key holder. Both
  terminal residuals close, the advisory ledger stops being the last line, and (B) is
  meaningfully safer than a hot wallet.
- If **no** → the counter stays advisory wherever it runs, and (B) ships with that written
  down. That is still shippable; what is not acceptable is shipping it while implying the
  counter is enforced.

> **RULED 2026-08-13 — the predicate is OURS until a vendor's docs say otherwise.** Do not
> block on an answer we cannot get today. Build the gate on our side, state plainly that we
> enforce it, and move it to the key holder later if a policy engine turns out to express
> it. The rule this protects: never imply the signer enforces something only we check.

Privy is proven for signing (five enclave-signed mainnet transactions, deny-by-default per
method, program allowlist on both sides). 1Claw's claim is custody plus **spend policy** —
which is exactly the half Privy has not been shown to cover. So the sequence is: ask both
the question above, then choose. Do not migrate a working signer for a capability nobody
has measured.

## Sequence

1. ~~Ratify (A) or (B)~~ — **RULED: (B), (A) preserved as a mode.**
2. ~~Gate the SSE POST mount~~ — **DONE.** Both halves now carry the gate or neither does.
3. ~~Ask the policy question~~ — **RULED: assume the predicate is ours; revisit on docs.**
4. **The `prepare_purchase` inversion** — look the pubkey up from the session, stop
   accepting it. Blocked on the identity ruling: it needs `account → wallet_id`.
5. **Durable spend ledger** — EFS, or the counter moves to whichever signer can hold it.
6. **Fix the provenance fail-open** — required before any external config loads, in either
   provider model. `_apply_origin_cap` is demotion-only, so a config that omits
   `pda_origins` earns `extracted`.
7. **Run the Grok and Claude-web tests**, reporting transport results separately from
   client-behaviour results.
8. **Then** the provider surface build, with the admission model ruled and both hosting
   models offered.
